## STOP_FIRST v=1

在改变运行状态、清目标和令牌前冻结。`at`是F103本地决定时刻，`event_at`是事件产生时刻；二者和F407时间不能直接相减。每条首因分part=0/1/2输出，用`boot、token、at`关联。字段为十进制，`boot、flags、valid、key mask、axis_flags`为十六进制。串口成功发送仅说明交给USART1，不证明PC已保存。

| part | 内容 |
| --- | --- |
| 0 | source、recovery、detail、原state、event_at、按键event/mask、下层/上层boot、link/motion token、原rpm/mm_s目标 |
| 1 | valid、控制/双轴/心跳年龄、控制记录序号、目标序号、控制generation、控制flags、owner、life、axes |
| 2 | 原轴flags/mode/fault、stop_req及合并重复次数merged |

source：1控制记录陈旧，2轴基本状态陈旧，3新鲜轴报告不安全，4按键普通STOP，5按键快速STOP，6按键授权释放，7授权超时，8首零确认超时。

recovery：7=`CTRL STALE`，8=`AXIS STALE`，9=`AXIS UNSAFE`，其余0；detail=116对应运行反馈门禁，112授权超时，118首零超时。

valid位：bit0控制记录存在且valid，bit1通过500ms控制门禁，bit2/3左/右轴valid，bit4/5左/右轴通过300ms门禁，bit6曾收到心跳。年龄`4294967295`表示无有效样本。轴新鲜不等于轴安全，还需查看flags、mode及fault。

按键event沿用UI枚举：STOP=2、K1_LONG=3、QUICK_STOP=5。key mask的bit0/1/2分别为K1/K2/K3防抖后的按下状态，取事件生成时的样本；K2长按为普通STOP，K3按下为快速STOP。

stop_req是本次决策预期创建的请求序号：普通STOP/释放对应0x110的8位请求序号，快速STOP对应0x080的16位停车序号。它是清目标前预测的下一序号，后续若原状态或链路门禁拒绝创建请求，不表示帧已经发送；以实际TX/主控收取日志核实。轴报告不安全分支直接进入Fail，不创建STOP请求，输出65535作为未知标记。快速停车序号也可能合法为65535，需结合source区分。

首条记录独立于普通队列，失败发送保留同一页重试。输出后仍保留现场；下一次授权重新准备时允许新记录。新授权遇到未输出完的首条时保留旧记录，新的异常只增加merged，待旧记录全部输出后才允许冻结新现场。日志任务每次最多输出一页，没有新增查询、重试运动命令或续租。

## 内存与验证

正式Keil同日志配置重建：基线2c60782占18336B，本版占18416B，净增80B，剩2064B，满足96B净增和2048B余量要求。冻结结构80B（含pending/page/armed），按键元数据进入现有布局空隙；UI事件将key_mask放在type后，ARMCC事件仍为8B、8项数组仍64B，未扩大队列或任务栈。主机GCC枚举大小与ARMCC不同，最终以正式map为准。

测试直接调用生产控制与UI代码，覆盖499/500ms控制边界、299/300ms轴边界、回绕、硬故障、真实防抖K3/K1事件、首因清目标前保留、日志队列满、UART失败重试和三页完成。已有双端授权/调速/停车/重授权100轮、真实bus mock与OLED日志开关等价测试保留。`Tests/run_tests.ps1 -DebugEnabled 0`和`1`执行对应回归；脚本同时补齐已有同步引擎链接源`app_sync_params.c`。

只读解析：`python Tests/analyze_stop_first.py <串口日志.txt>`，可加`--json`；缺页明确输出`missing`。解析器回归：`python -m unittest discover -s Tests -p test_analyze_stop_first.py`。

上电前两端串口同时开始保存，先低速后正反向400rpm。若再停车，首先找F103三页`STOP_FIRST`，再按token/命令序号与主控首停和记录失败关联。真实断线、陈旧轴和控制记录仍须在原门限保护停车。

正式构建、map、调用栈、固件哈希和双侧复测步骤统一存放于F407工程`Docs/CAN_TIMING_20261108`。静态已知栈余量全部至少256B，现场历史空闲栈也按本轮256B门槛验收；软件检查不替代现场水位。当前状态：软件验证完成，待实物验收。
