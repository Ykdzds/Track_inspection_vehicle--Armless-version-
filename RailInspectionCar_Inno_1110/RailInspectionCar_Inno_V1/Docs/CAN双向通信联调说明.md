# CAN双向通信联调说明

日期：2026-10-09

2026-10-19当前接入说明：本文件早期只读联调结论保留为历史背景；当前支持独立CAN控制测试构建及HMI控制权遥测，遵循现用V1.1文档和《CAN遥测补齐与上位机低速测试接入记录_20261019.md》。链路心跳失联期限1000ms、目标租期100～300ms、停车绝对上限30000ms；不得用旧500ms链路期限、20000ms停车上限或旧机械限速硬编码。

## 1. 范围

通信遵循《STM32与RK3588上层感知层CAN总线通信协议 V1.0》。
本固件可用于双向链路联调，但尚无CAN分析仪或RK实物验收记录。
本阶段不接受CAN运动、授权、使能、停车、里程清零及采集控制，不改变遥控和CLI控制方式。
CAN断线仅使CAN链路及上层缓存失效，不新增伺服停车或看门狗触发条件。

## 2. 固件与硬件准备

- 默认`APP_CAN_ENABLED=1`、`APP_CAN_DEBUG_ENABLED=0`、`APP_CAN_CONTROL_ENABLED=0`、`APP_CAN_STOP_PARAMETERS_APPROVED=0`。
- 双方统一使用经典CAN、500 kbit/s、标准数据帧、DLC=8；不用CAN FD、扩展ID或远程帧。
- CAN1使用PA11 RX、PA12 TX；APB1为42 MHz，Prescaler=6、BS1=11、BS2=2、SJW=1。
- 主控与上层均需正确供电的CAN收发器，不能直接将MCU CAN引脚接到CANH/CANL。
- 确认CANH、CANL及信号参考地接线；总线两端各设置120 Ω终端，断电后检查总线等效终端约60 Ω，避免重复终端。
- 实物先固定车辆、保持未授权，使用分析仪验证后再接RK。

当前构建检查使用`Tests/build_can_control.ps1`，临时工程输出在独立`D:\CodexBuild\RailInspectionCar`目录，不生成HEX、不覆盖正式下载目录、不自动烧录。该脚本检查正式CAN关闭、CAN开启、HMI共存及各轴配置，不能把矩阵中的单轴或只读产物当作正式固件。

当前工作区用户已将CAN_DEBUG、CAN_CONTROL和STOP_PARAMETERS_APPROVED的默认宏改为1，本次保留这些未提交改动。因此直接点击当前Keil工程编译会启用CAN控制；正式关闭配置须显式指定CAN_CONTROL=0、STOP_PARAMETERS_APPROVED=0，独立测试配置指定CAN_ENABLED=1、CAN_CONTROL=1、STOP_PARAMETERS_APPROVED=1、SERVO_READONLY_TEST=0。下载前核对实际宏、源码哈希与编译版本，不能只看同名文件。

## 3. Flash保留要求

扇区11的`0x080E0000～0x080FFFFF`用于身份及配置追加日志，程序链接范围仅为前896 KiB。
该链接限制只防止代码占用日志区，不自动保证下载器不擦除日志区。

2026-10-11更新：CAN与UART5 HMI共用启动身份服务，每次MCU启动只追加一条日志。即使APP_CAN_ENABLED=0，HMI仍需持久化启动号，因此仍写一次日志；CAN模块自身不再单独写入。身份失败时CAN拒绝新会话，HMI发布未知身份，不影响既有遥控及CLI安全策略。

- 下载器选择必要扇区擦除，确认保留扇区11；不要使用全片擦除。
- 无法确定工具擦除策略时先停止下载，核验下载设置及厂商工具行为。
- 首次使用应确认日志区为空白或本固件兼容日志；区域损坏、非兼容数据、写入失败或编号耗尽会拒绝新CAN会话。
- 不自动擦除损坏区域，也不在运行中擦写Flash。
- 全片擦除或重新编号只能作为双方停机维护操作，并清除双方历史会话缓存；不能只擦主控后继续沿用RK旧会话。
- CubeMX重新生成后执行配置检查，并复核Keil链接区和下载设置。

## 4. 联调顺序

1. 主控上电，USART1执行`can status`，检查`enabled=1 task=1 identity=0`。
2. 检查`bus=3`表示CAN驱动就绪；此时没有上层握手，`link`尚未等于4是正常情况。
3. 分析仪或RK读取主控`0x101`启动信息，上层发送`0x102`启动信息及`0x104`双方boot回显。
4. 上层完整接收`0x300/0x301/0x302`承载的`0x01`会话邀请，核验CRC，使用真实boot、令牌及邀请序号返回`0x105`。
5. 主控成功发送`0x106`后，上层按协议发送三个递增且健康的`0x100`心跳，随后持续每100 ms发送。
6. 主控进入`link=4`，上传`0x02`能力和`0x10`最新配置，并运行基本与扩展状态调度。
7. 用`can stat`检查RX/TX成功持续增加，用`can upper status`查看上层各类记录的有效性与年龄。

不要等到`link=4`才开始上层心跳，否则会与主控等待健康心跳的门禁互相等待。
默认链路超时500 ms；只收到任意原始帧不代表握手或健康心跳成立。
健康心跳标志须符合协议，包括健康位bit0有效、故障位bit6未置位。
会话号、boot和序号必须从真实帧解析，不得硬编码测试向量的示例值。

`can status`关键状态：

| 字段 | 值 | 含义 |
|---|---:|---|
| bus | 0/1/2/3/4 | 关闭/等待初始化/等待运行/就绪/恢复退避 |
| link | 0/1/2/3/4 | 身份失败/等待上层/等待会话确认/等待健康心跳/就绪 |
| identity | 0 | 身份日志准备成功，其他值需排查日志准备失败原因 |
| control | 0 | 不开放CAN运动控制 |

## 5. 查询与上层状态

- 普通命令`0x08`查询记录，参数1为记录类型，参数2为0；`0x0A`查询能力/配置，两个参数均为0。
- 按协议使用当前令牌和请求序号；同序同内容重传可去重，同序不同内容拒绝，普通请求限频10次/秒。
- `0x120`表示请求接受/拒绝；`0x121`表示业务完成/失败，两者不是同一个阶段。
- 查询所需记录的提交帧CAN发送成功后才报告完成，不表示RK应用已经收到或处理。
- `0x080`不执行停车，拒绝信息通过`0x11`控制记录回传；不能把收帧或拒绝响应当作已停车。
- 上层扩展记录使用`0x310/0x311/0x312`，最大256字节，须在200 ms内完整校验并满足类型、会话、序号和业务有效标志。
- 半条记录、CRC错误或重复旧记录不能刷新业务有效数据的年龄；`present=1`不一定`valid=1`。
- 定位生产者为RK，不将收到的定位记录原样反发给RK。
- 底盘参数直接由工程配置生成；参数变更后版本随配置指纹更新，重连或查询取得完整最新配置。
- 电池、机械臂、照明、制动及DI3实体反馈未接入时显示未知，不显示虚假的正常值。

编码例子见`Docs/CAN_V1_编码测试向量.md`。向量由生产代码生成，其时间仅是测试步进，
不是实际周期或总线抓包；生成器未运行完整APP周期调度，不可据此推断全部周期帧的时序。

## 6. USART1诊断

将`APP_CAN_DEBUG_ENABLED`设为1并重新编译可启用持续诊断；默认0仍可使用上述三个查询命令。

- `RX`：接收到的CAN帧；`SUBMIT`：邮箱提交，不是发送成功。
- `TX_OK`：控制器报告CAN发送成功，不是RK业务确认；`TX_FAIL`：发送失败。
- 每帧日志包含方向、时间、标准ID、DLC及原始8字节；每秒输出一次统计。
- 逐帧日志合计最多20行/秒，总预算3000字节/秒，并为CLI预留512字节。
- 队列或USART1空间不足时跳过完整日志并计数，不等待，不保证打印满负荷CAN的每一帧。
- 分别检查`rx_drop`、`queue_drop`、`record_fail`和`log_skip`，不要把日志跳过等同于总线丢帧。

CAN任务和ISR不直接调用`printf()`，格式化及DMA输出由CLI任务处理。

## 7. 验收记录

- 验证任意上电顺序、主控重启、RK重启、拔线恢复、无ACK及Bus-off恢复。
- 对照协议核验实时速度、轴状态、位置、轮转估算里程、有效性、未知值、配置版本及单位。
- 验证查询接受/完成、重复请求、同序冲突、CRC/缺段拒绝及上层数据过期。
- 验证不支持的运动请求不会产生伺服写请求、授权或停车动作。
- 记录总线占用，目标平均不超过20%、持续不超过30%；记录USART1丢弃、USART2错误增量、速度配对率及任务栈高水位。
- 验证遥控、CLI、同步、K1停车和看门狗恢复仍按原策略运行，不新增持续RS485错误或看门狗复位。

主机模拟测试、Keil编译及静态栈检查只能作为软件证据；物理接线、波形、实际实时性及上下层应用互操作仍需实物验收。
