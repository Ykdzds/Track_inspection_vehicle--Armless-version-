# 轨道巡检车底盘软件分阶段设计方案

## 1. 文档目的

本文档以当前工程目录 `5.工程代码/RailInspectionCar_V1_XZ` 为唯一软件基线，重新梳理当前代码、外设配置、工程组织和第一阶段实施路径。

第一阶段以伺服电机底层控制为主，目标是建立可测试、可扩展、可诊断的伺服控制基础：

- USART2 + RS485 + Modbus-RTU；
- USART2 RX DMA Circular 模式、二进制接收、环形缓冲区和响应解析；
- 伺服状态、故障和控制命令；
- TIM9/TIM11 动态脉冲与方向输出；
- 速度、位置、加速度和减速度统一接口；
- 梯形加减速，必要时自动退化为三角速度曲线；
- BEEP、LED、KEY 和 USART1 调试接口；
- 为后续双轴同步、编码器反馈、三级停车和安全联锁预留接口。

第一阶段明确不使用 `PD0`、`PD1`、`PD5`，不把软件功能当作实体急停或硬件安全回路。

| 参数 | 当前确认值 | 软件用途 |
|---|---:|---|
| 伺服站号 | 1 | Modbus-RTU 从站地址默认值 |

| 数据格式 | 8N1 | 8 位数据、无校验、1 位停止位 |
| 轮胎直径 | 185 mm | 车轮线速度和脉冲频率换算 |
| 轮胎周长 | 约 0.581195 m | `pi * 0.185` |
| 出厂脉冲当量 | 1000 脉冲/转 | 未启用电子齿轮时的默认换算 |

在轮胎直径 185 mm、1000 脉冲/转且未启用电子齿轮时：

```text
每米脉冲数 = 1000 / 0.581195 ≈ 1720.59 pulse/m
脉冲频率 = 目标速度(m/s) * 1720.59 Hz
```

例如目标速度 `1.0 m/s` 时，理论脉冲频率约为 `1720.59 Hz`。该数值是第一阶段默认换算值，最终仍需结合驱动器电子齿轮、脉冲输入模式、方向定义和现场实测标定。

TIM2 的配置为 `Prescaler=168-1`、`Period=1000-1`。在 168 MHz 定时器时钟条件下，更新周期约为 1 ms，当前中断回调调用 `key_scan()`。按键模块内部每 10 次采样处理一次，因此实际按键判断周期约为 10 ms。

TIM9 和 TIM11 当前均为：

```text
Prescaler = 200 - 1
Period    = 1680 - 1
Pulse     = 840
```

按当前 APB2 定时器时钟 168 MHz 计算，输出约为 500 Hz、50% 占空比。这只是固定测试波形，尚未实现速度换算、位置计数或梯形规划。

### 3.4 当前代码功能和问题

#### 3.3.1 应用入口和任务

`app_init()` 当前做了以下工作：

```c
__HAL_UART_ENABLE_IT(&huart2, UART_IT_IDLE);
HAL_UART_Receive_DMA(&huart2, (uint8_t *)rxdat, UART2_DMA_RXLENGT);
HAL_TIM_Base_Start_IT(&htim2);
HAL_IWDG_Refresh(&hiwdg);
```

自建任务包括 `start_task`、`key`、`task2` 和 `iwdg`。其中：

- `start_task` 创建其他任务后自删除；
   - `key` 任务每约 100 ms 调用一次 `key_handle()`，按键扫描由 TIM2 中断调用 `key_scan()`；
- `task2` 目前为空；
- `iwdg` 每 500 ms 喂一次看门狗；
   - 当前通过 `USE_MY_FREERTOS_INIT=1` 选择自有入口，运行时不调用 CubeMX 的 `MX_FREERTOS_Init()`，因此不创建 `defaultTask`；但 `freertos.c` 和 `.ioc` 中仍残留 CubeMX 的 `defaultTask` 定义，长期应清理或明确标注为非使用代码。

主要风险：

   1. 源码层仍保留两套任务定义，后续重新生成代码时容易误开关或重复创建。
   2. `task2` 尚未承担伺服通信或运动功能。
   3. 关键任务没有心跳检查，单纯周期喂狗不能发现某个功能任务已经失效。
   4. `vTaskDelay(100)` 没有使用统一的毫秒宏；按键扫描虽由 TIM2 完成，但事件消费延迟可能达到约 100 ms。

#### 3.3.2 RS485

当前 `bsp_rs485.c` 的代码仍按“停止 DMA、根据 DMA 剩余计数计算长度、重启 DMA”的旧 Normal 模式思路编写；而工程配置和 `usart.c` 已改为 USART2 RX DMA Circular。因此，底层代码必须同步改造为 Circular DMA 读指针模型，不能继续在 IDLE 中调用 `HAL_UART_DMAStop()`。

目前不能作为完整 Modbus-RTU 通信层，问题包括：

- 接收数组使用 `char`，不适合二进制协议；
- 发送函数使用 `strlen()`，遇到 `0x00` 会提前截断；
- 清空缓存使用 `strlen()`，无法按二进制长度处理；
- 没有软件环形缓冲区；
- 没有帧队列、事务管理和并发访问保护；
   - 旧实现与 Circular 配置不一致，继续 Stop/Restart 会破坏连续接收；
   - 硬件 TTL 转 RS485 收发器自带自动流向控制，软件不使用 DE/RE GPIO；
   - 仍需确认发送完成和自动换向的时序，必要时等待 UART `TC`；
- 没有 CRC16、站号、功能码、长度和异常响应校验；
- 没有超时、重试、离线判定和统计计数；
- `uart2_dma_data_handle()` 尚未形成完整的接收处理调用链。

因此，第一阶段必须先重构 RS485 底层，再接入伺服设备层。

#### 3.3.3 按键

当前按键模块已加入双击状态字段、双击超时和双击标志，具备短按、长按、双击的基础识别逻辑，但存在以下问题：

   - `key_times`、`double_times` 的计时单位和阈值仍应统一为明确的毫秒或采样次数；
- 中断和任务共享标志位，没有事件队列或并发保护；
   - `key_handle()` 目前主要清除标志，没有向应用发布实际事件；
- 按键扫描与按键业务耦合，后续更换按键功能会扩大修改范围。

第一阶段应改成“定时采样、事件识别、队列发布、任务消费”的结构。

#### 3.3.4 LED 和 BEEP

LED 和蜂鸣器已经有基础 GPIO 封装，但：

- LED 的 `LED_ON=0`、`LED_OFF=1` 与 `set_led()` 的电平写入语义容易混淆；
- LED 可被多个任务直接写入，可能互相覆盖；
- BEEP 只有直接开关，没有模式、节拍和故障提示管理；
- 当前没有统一的系统状态到灯光/声音的映射。

第一阶段可以保留底层 GPIO 接口，同时增加统一状态显示任务。

#### 3.3.5 调试串口

USART1 当前只有 `fputc()` 重定向，能输出 `printf`，没有接收、行缓冲、命令解析和参数校验。第一阶段需要增加最小 CLI，用于单轴低速调试和故障诊断，但不能绕过运动状态限制强制运行。

## 6. RS485 和 Modbus-RTU 设计

### 6.1 二进制收发接口

发送接口必须显式携带长度，不能使用字符串函数：

```c
typedef enum
{
    RS485_OK = 0,
    RS485_BUSY,
    RS485_TIMEOUT,
    RS485_OVERFLOW,
    RS485_HAL_ERROR
} rs485_status_t;

rs485_status_t rs485_init(void);
rs485_status_t rs485_send(const uint8_t *data, uint16_t length);
uint16_t rs485_read(uint8_t *data, uint16_t capacity);
uint16_t rs485_available(void);
```

### 6.2 DMA 接收方案

当前工程的 USART2 RX DMA 已配置为 `Circular` 模式，第一阶段应直接采用“DMA 循环缓冲区读指针 + 软件环形缓冲区”的方案，不得继续沿用停止 DMA、计算长度、重启 DMA 的旧 Normal 模式逻辑。

实施要求：

1. DMA 接收数组使用 `uint8_t`，因为 Modbus-RTU 是二进制协议；
2. 初始化时启动一次 `HAL_UART_Receive_DMA()`，后续接收过程中不因 IDLE 事件停止并重启 DMA；
3. 维护 DMA 缓冲区的上次读取位置，根据当前 DMA 写入位置计算新增字节；
4. 在 UART IDLE、DMA 半传输和全传输事件中搬运新增数据；如果当前 HAL 工程只启用了 IDLE 回调，也必须保证协议任务能够周期性推进读指针；
5. 新增数据写入软件环形缓冲区，由 Modbus 协议任务按字节提取和组帧；
6. 不能假设一次 IDLE 中断对应一个完整 Modbus 帧，必须支持半帧、粘包、连续多帧和异常帧；
7. 软件环形缓冲区溢出时丢弃当前受损帧并记录错误计数，不能静默覆盖尚未解析的数据；
8. 通过任务通知、事件标志或队列通知协议任务，避免在中断中执行完整协议解析。

推荐 DMA 缓冲区和软件环形缓冲区初始容量均按 512 字节设计，最终应结合最大帧长、轮询周期和总线负载实测确认。Circular DMA 的核心目标是连续接收，软件环形缓冲区的核心目标是隔离中断接收与任务解析。

### 6.3 RS485 方向控制

当前 TTL 转 RS485 收发器自带自动流向控制，工程不使用 DE/RE GPIO，软件不得增加或依赖 DE/RE 引脚。

软件只需负责：

- 对发送接口加互斥，保证同一时刻只有一个 Modbus 帧发送；
- 发送前检查总线事务状态，避免多个任务直接调用 HAL 导致帧交错；
- 使用 DMA 或中断发送后等待 UART `TC`，确保最后一个停止位已经发出，为自动流向收发器留出可靠的换向时序；
- 发送完成后立即进入接收等待状态，不执行任何 GPIO 方向切换；
- 在自动收发器的实际硬件上验证短帧、连续帧、最高负载和异常中断情况下的收发切换。

RS485 的自动收发方向与伺服脉冲接口的正反转方向是两个不同概念。伺服脉冲方向仍由对应的方向 GPIO 和脉冲输出模块负责，不能把两者混为同一个“方向控制”功能。

### 6.4 Modbus-RTU 事务状态机

单总线同一时刻只允许一个未完成事务：

```text
IDLE
  -> BUILD_REQUEST
  -> SET_TX
  -> SEND
  -> WAIT_TX_COMPLETE
  -> SET_RX
  -> WAIT_RESPONSE
  -> VALIDATE
  -> COMPLETE
```

错误路径统一进入：

```text
CRC_ERROR / FORMAT_ERROR / EXCEPTION / TIMEOUT
  -> RETRY
  -> OFFLINE_OR_ERROR
```

必须检查：

- 站号是否匹配；
- 功能码是否匹配；
- 异常功能码是否出现；
- 响应长度是否符合请求；
- CRC16 是否正确；
- 接收是否在规定超时时间内完成；
- 连续失败次数和最后成功时间。

建议每个事务最多重试 2 次，具体值通过台架测试调整。连续失败超过阈值后，将对应伺服标记为离线，禁止持续发送运动控制命令。

### 6.5 Modbus 帧接口

```c
typedef struct
{
    uint8_t  slave_id;
    uint8_t  function;
    uint16_t address;
    uint16_t quantity;
    const uint16_t *write_data;
    uint16_t write_count;
} modbus_request_t;

typedef struct
{
    uint8_t  slave_id;
    uint8_t  function;
    uint8_t  data[MODBUS_MAX_DATA];
    uint16_t length;
} modbus_response_t;

modbus_status_t modbus_master_execute(
    const modbus_request_t *request,
    modbus_response_t *response,
    uint32_t timeout_ms,
    uint8_t retry_count);
```

具体使用 03、06、10 或其他功能码必须以 AIMtor 驱动器协议表为准。

## 7. AIMtor 伺服适配层

### 7.1 适配层职责

AIMtor 适配层负责把工程单位和运动意图转换为厂家协议对象：

- 伺服站号；
- 伺服工作模式；
- Servo ON/OFF；
- 目标速度或目标位置；
- 停止方式；
- 报警复位；
- 状态字；
- 实际速度和实际位置；
- 故障码；
- 设备在线/离线状态。

### 7.2 统一数据结构

```c
typedef enum
{
    SERVO_MODE_SPEED = 0,
    SERVO_MODE_POSITION,
    SERVO_MODE_JOG
} servo_mode_t;

typedef struct
{
    uint8_t  slave_id;              // 伺服站号
    servo_mode_t mode;              // 控制模式
    float    target_velocity_mps;  // 目标线速度，单位 m/s
    float    target_position_m;    // 目标位移，单位 m
    float    acceleration_mps2;    // 加速度，单位 m/s2
    float    deceleration_mps2;    // 减速度，单位 m/s2
    uint32_t timeout_ms;            // 动作超时
} servo_motion_cmd_t;

typedef struct
{
    uint8_t online;                // 通信在线
    uint8_t enabled;               // 伺服已使能
    uint8_t running;               // 伺服运行中
    uint8_t fault;                 // 存在故障
    uint16_t status_word;          // 厂家状态字
    uint16_t fault_code;           // 厂家故障码
    float actual_velocity_mps;     // 实际线速度
    float actual_position_m;       // 实际位置
    uint32_t last_success_tick;    // 最后一次成功通信时间
} servo_state_t;
```

建议接口：

```c
servo_status_t servo_init(const servo_config_t *config);
servo_status_t servo_enable(uint8_t slave_id);
servo_status_t servo_disable(uint8_t slave_id);
servo_status_t servo_execute(const servo_motion_cmd_t *command);
servo_status_t servo_stop(uint8_t slave_id, servo_stop_type_t type);
servo_status_t servo_read_status(uint8_t slave_id, servo_state_t *state);
servo_status_t servo_read_fault(uint8_t slave_id, uint16_t *fault_code);
servo_status_t servo_reset_fault(uint8_t slave_id);
```

上层只传入 `m`、`m/s`、`m/s2` 等工程单位。所有单位换算、寄存器打包和符号转换集中在适配层。

### 7.3 协议待确认项

| 控制 | 使能、停止、报警复位寄存器和位定义 |

## 8. 脉冲输出和运动规划

### 8.1 机械标定参数

必须建立统一标定参数：

```c
typedef struct
{
    float wheel_diameter_m;       // 车轮直径
    float reduction_ratio;        // 减速比
    uint32_t motor_pulses_rev;    // 电机一转所需脉冲数
    float max_velocity_mps;       // 最大线速度
    float max_acceleration_mps2;  // 最大加速度
    float max_deceleration_mps2;  // 最大减速度
    uint8_t direction_invert;     // 方向是否反相
} motion_axis_config_t;
```

脉冲当量需要结合电子齿轮和实测结果计算：

```text
车轮周长 = pi × 车轮直径
每个脉冲位移 = 车轮周长 / 车轮每转对应的有效脉冲数
脉冲频率 = 目标线速度 / 每个脉冲位移
```

不能只根据电机铭牌推定脉冲当量。

### 8.2 TIM 动态脉冲

当前固定 PWM 应封装为：

```c
servo_pulse_status_t servo_pulse_init(void);
servo_pulse_status_t servo_pulse_start(axis_id_t axis, uint32_t frequency_hz);
servo_pulse_status_t servo_pulse_set_frequency(axis_id_t axis, uint32_t frequency_hz);
servo_pulse_status_t servo_pulse_set_direction(axis_id_t axis, int8_t direction);
servo_pulse_status_t servo_pulse_stop(axis_id_t axis);
void servo_pulse_disable_all(void);
```

在定时器时钟为 `timer_clk_hz` 时：

```text
ARR = timer_clk_hz / 目标频率 - 1
CCR = (ARR + 1) / 2
```

必须限制：

- 目标频率不能为零或超出定时器和驱动器上限；
- `ARR` 不能小于硬件允许值；
- 频率变化不能造成无效脉冲；
- 方向切换前必须先降到零；
- 停止顺序为停脉冲、关闭 PWM、关闭 AM26C31 输出使能；
- PC8/PC9 的有效电平必须在 BSP 中抽象，不能由上层直接写 GPIO。

初始安全态应保持：

```text
PC8 = 0
PC9 = 1
TIM9/TIM11 不输出有效脉冲
```

### 8.3 统一运动控制接口

建议最终向上层提供：

```c
motion_status_t motion_start(const servo_motion_cmd_t *left,
                             const servo_motion_cmd_t *right);
motion_status_t motion_set_velocity(float left_mps,
                                    float right_mps,
                                    float acceleration_mps2);
motion_status_t motion_move_distance(float distance_m,
                                     float velocity_mps,
                                     float acceleration_mps2,
                                     float deceleration_mps2);
motion_status_t motion_stop(motion_stop_type_t type);
motion_status_t motion_get_state(motion_state_t *state);
```

这些接口只处理运动意图和状态，不直接拼 Modbus 帧。

### 8.4 梯形和三角速度规划

完整位置动作包含：

```text
加速段 -> 匀速段 -> 减速段 -> 速度为零
```

当目标距离不足以达到设定速度时，改用三角速度曲线：

```text
加速段 -> 减速段
```

规划器输出每个控制周期的目标速度，运动任务再把目标速度转换为脉冲频率。规划器需要处理：

- 目标速度正负号；
- 最大速度和加速度限幅；
- 方向切换前减速到零；
- 位置误差和剩余距离；
- 动作超时；
- 软停止和快速停止；
- 目标被新命令覆盖时的平滑接管。

建议运动任务周期为 1～5 ms，规划计算在任务中完成，不能在高频 PWM 输出中断中执行浮点运算。

## 9. FreeRTOS 任务设计

第一阶段建议任务职责如下：

| 任务 | 周期或触发 | 职责 |
|---|---|---|
| `motion_task` | 1～5 ms | 速度规划、频率更新、运动状态 |
| `servo_comm_task` | 事件加周期轮询 | Modbus 事务、状态、故障和在线检测 |
| `key_task` | 5 ms | 取按键事件并分发 |
| `status_task` | 50 ms | LED、BEEP、通信状态显示 |
| `debug_task` | 接收队列触发 | USART1 命令解析 |
| `health_task` | 50～100 ms | 任务心跳、堆栈和错误统计 |
| `iwdg_task` | 100～500 ms | 仅在关键任务均正常时喂狗 |

建议任务间通过队列、事件组和互斥锁通信：

```text
debug_task
  -> motion_command_queue
motion_task
  -> servo_command_queue
servo_comm_task
  -> servo_state_queue
status_task / health_task
```

运动任务不应同步等待 Modbus 响应。通信任务只发布设备状态，运动任务依据状态决定是否继续、减速或停止。

必须最终关闭或删除未使用的 CubeMX `defaultTask`，避免两套调度入口造成误判。

## 10. KEY、LED、BEEP 和 USART1

### 10.1 按键事件

按键模块采用以下状态机：

```text
稳定释放
  -> 消抖按下
  -> 稳定按下
  -> 长按已确认
  -> 消抖释放
  -> 等待双击
```

建议定义：

```c
typedef enum
{
    KEY_EVENT_SHORT = 0,
    KEY_EVENT_LONG,
    KEY_EVENT_DOUBLE
} key_event_type_t;

typedef struct
{
    uint8_t key_id;
    key_event_type_t type;
    uint32_t tick;
} key_event_t;
```

规则：

- 采样周期 1～5 ms；
- 消抖时间约 20 ms，实测调整；
- 长按超过设定阈值只产生一次；
- 第一次短按后在双击窗口内再次短按，产生双击；
- 双击窗口超时才确认单击；
- 事件进入 FreeRTOS 队列；
- 中断只负责采样或投递，不直接控制伺服。

### 10.2 LED 和 BEEP 状态

建议由 `status_task` 统一控制：

| 状态 | LED 建议 | BEEP 建议 |
|---|---|---|
| 上电自检 | 全部短亮 | 短鸣一次 |
| 待机 | 绿色慢闪 | 无 |
| 运行 | 绿色常亮或快闪 | 无 |
| 通信异常 | 黄色或蓝色周期闪烁 | 周期提示 |
| 伺服故障 | 红色周期闪烁 | 故障节拍 |
| 禁止运行 | 红色常亮 | 无或短提示 |

LED 的有效电平应统一在驱动层定义，解决当前 `LED_ON` 宏与底层 GPIO 电平语义不一致的问题。

### 10.3 USART1 调试 CLI

建议实现：

```text
help
servo status <id>
servo fault <id>
servo enable <id>
servo disable <id>
servo reset <id>
servo vel <id> <m/s> <acc>
servo move <id> <m> <m/s> <acc> <dec>
servo stop <id>
motion state
motion config
log level <0-3>
```

CLI 必须具备：

- 行缓冲；
- 命令和参数数量检查；
- 数值范围检查；
- 站号检查；
- 当前状态检查；
- 统一错误码；
- 禁止在故障或未初始化状态下直接运行；
- 后续接入安全状态机后，不允许 CLI 绕过安全许可。

## 13. 后续安全停车软件衔接

第一阶段不使用 `PD0`、`PD1`、`PD5`，但接口设计要为后续安全状态机保留入口：

```text
POWER_OFF
  -> SELF_TEST
  -> STANDBY
  -> RUN
  -> NORMAL_STOP
  -> FAST_STOP
  -> FAULT_LATCHED
  -> EMERGENCY_STOP
```

后续阶段接入安全链后：

- 硬件急停必须直接切断危险动力，不依赖 RTOS；
- 软件只读取安全链状态并禁止运动；
- 安全条件恢复后不得自动重启；
- 伺服状态、抱闸、接触器和安全输入必须形成一致的状态机；
- 正常停车、快速停车和实体急停要分别测试停车时间、停车距离和抱闸时序。

第一阶段只需在 `motion_stop()`、`servo_disable()`、`servo_pulse_disable_all()` 等接口上预留统一停止入口，不能假设后续安全输入已经存在。

## 14. 关键风险和处理原则

1. **协议风险：** 未确认 AIMtor 寄存器时不得直接写入伺服控制逻辑。
2. **数据风险：** Modbus 是二进制协议，禁止使用 `strlen()` 计算帧长度。
3. **通信风险：** USART2 RX 已配置为 Circular，但底层代码仍可能残留 Normal 模式的停止/重启逻辑；若不重构为 DMA 读指针推进模型，仍会造成连续接收中断、丢帧或重复取数。
4. **运动风险：** 固定 PWM 只能验证波形，不能代表可控速度或位置。
5. **时序风险：** 方向、脉冲、Servo ON/OFF 和抱闸必须有明确先后顺序。
6. **任务风险：** 看门狗必须检查任务心跳，不能只设置一个周期喂狗任务。
7. **调试风险：** CLI 不能跳过状态检查直接驱动电机。
8. **安全边界：** 软件停车不能替代硬件急停、电源按钮、主动力分断和失电抱闸。
9. **参数风险：** 轮径、减速比、电子齿轮和脉冲当量必须实测标定。
10. **引脚边界：** 第一阶段不得读取或使用 `PD0`、`PD1`、`PD5`。

## 15. 第一阶段最终结论

当前工程适合从以下顺序进入实现：

```text
统一任务入口
  -> RS485 二进制 DMA 和环形缓冲区
  -> Modbus-RTU 主站事务层
  -> AIMtor 伺服适配层
  -> TIM9/TIM11 动态脉冲
  -> 单轴运动规划
  -> 双轴同步
  -> KEY/LED/BEEP/USART1 测试闭环
```

当前工程已经具备硬件初始化、基础 FreeRTOS、自建任务、USART2 DMA + IDLE 原型、三按键扫描、LED/BEEP GPIO 和 USART1 `printf` 基础，但尚不具备完整的 RS485/Modbus、伺服控制、动态脉冲、运动规划和故障闭环。

第一阶段的完成标准不是“电机能够转动”，而是：

- 能可靠发送和接收二进制 Modbus 帧；
- 能区分正常响应、CRC 错误、超时和伺服故障；
- 能通过统一工程单位控制速度、位置和加减速度；
- 能输出受限的动态脉冲和可验证的梯形/三角速度曲线；
- 能在单轴和双轴测试中保持明确的状态和错误边界；
- 能为后续三级停车和硬件安全联锁提供稳定的软件入口。

在厂家协议表、机械脉冲当量和驱动器运行时序没有正式确认前，第一阶段应先完成通信仿真、单轴台架和低速空载测试，不直接进入载人或高速度整车运行。
