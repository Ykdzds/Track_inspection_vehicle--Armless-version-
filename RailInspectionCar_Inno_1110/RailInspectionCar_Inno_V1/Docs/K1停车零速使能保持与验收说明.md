## 1. 行为与边界

正常遥控运行时，K5短按立即撤销授权、目标置零、停止同步补偿，随后沿用独立K5减速度受控停车。选中轴均完成速度0写应答、两次新实际零速反馈，并异步回读确认使能配置有效后，进入人工停车锁存：保持原使能、红灯亮、未授权。

本行为是人工受控停车保持，不是断能急停、DI3或STO。软件使能回读只证明当前接线约定下的使能配置，不能替代独立硬件SON反馈；停车性能和实际保持力需要实测。

- LEFT_ONLY、RIGHT_ONLY、BOTH均按当前选中轴执行，BOTH必须全部确认。
- 正常调速斜坡、K5及失联减速度、驱动器加减速参数、速度P同步参数不变。
- 运行期保持独立于`APP_SERVO_STARTUP_HOLD_ENABLED`，开关0仍可保持已使能轴；不自动使能原本失能的轴，不执行设零或模式重配。
- 正常零速使能待机下短按K5，同样确认保持，不制造失能窗口。
- CLI期间、模式准备期间的K5继续立即撤权并尽力失能；真实故障、通信异常、人工急停及K6测试仍优先执行原安全流程。

## 2. 重新授权

停车与使能确认期间消费K5长按，不能缓存为“停完自动启动”。重复短按不重启停车或延长原期限。

保持完成后，摇杆回中并产生一次新的K5长按，且链路新鲜、启动门禁通过、所有选中轴在线、实际零速、反馈新鲜无故障、使能及速度模式核验有效时，才解除人工锁存并重新授权。从零命令开始，生成新授权代次，重建同步和遥控相对位置差基准，不恢复旧速度。成功接管无需失能、重新使能或模式配置。

无线失联、恢复及旧长按均不能解除锁存。手动扰动出现短暂非零反馈时保持使能，必要时补写速度0；此时不能重新授权，须恢复实际零速后再次产生新的长按。

遥控K5锁存期间，`servo debug on left/right`拒绝创建CLI会话，不能借CLI绕过。查询、停止、失能仍允许。CLI自身K5锁存的原显式恢复规则保持不变。

## 3. 诊断

执行：

```text
remote servo status
```

新增行示例：

```text
k5_hold state=2 valid=1 mask=3 confirmed=3 enabled=3 zero=3 disturbed=0 failure=0 authorized=0
```

| 字段 | 含义 |
| --- | --- |
| `state` | 0未进入，1保持确认，2已建立保持，3安全失败 |
| `mask` | 当前保持选中轴；1左、2右、3双轴 |
| `confirmed` | 本次申请后取得新鲜使能回读证明的轴掩码 |
| `enabled` | 当前快照中使能配置有效的轴掩码 |
| `zero` | 在线、模式正确、反馈新鲜无故障且实际零速的轴掩码 |
| `valid` | 运行期保持证明有效，不等于已授权或当前实际零速 |
| `disturbed` | 保持期间有选中轴实际速度非零，须等待恢复零速 |
| `failure` | 0无；1反馈/模式/门禁异常；2使能回读失败、失配或过期；3补写0失败；4其他安全退出 |
| `authorized` | 遥控运动授权；正常K5保持应为0 |

只有`valid=1`且`zero=mask`，才能说明零速保持当前有效；BOTH必须`confirmed=enabled=zero=mask=3`。确认失败、反馈过期、离线、模式失效、异常失能或补写0失败均退出保持、尽力失能并锁存，不能由长按绕过。

原停车诊断继续报告原因、阶段、期限、零速确认掩码及响应耗时；新增停车阶段`HOLD_CONFIRMING`，枚举值追加为6，不改变既有编号。使能确认仍受原停车期限约束。

红灯追加人工K5锁存条件，正常保持不新增持续蜂鸣。新授权成功后解除人工红灯条件，真实故障仍优先。

## 4. 无线显示

沿用冻结版32字节协议和遥控固件：

- 停车及保持确认期间：系统状态8“停车中”。
- 保持完成：系统状态9“K5急停/人工锁存”；实际使能位如实为1、授权位为0。
- 保持有效且实际零速：模式7、零速保持标志有效；扰动期间不发布零速保持有效。
- 真实异常：状态10，清除零速保持有效标志，不伪装正常待机。

ACK装载成功不等于遥控器已接收。无线帧号、布局、CRC、单位及编号均未改变。

## 7. 下载后无线失联、RS485变慢与闪屏修复

2026-10-09用户反馈：遥控首页在LOST/RX之间切换，S、M显示UNK，随后持续LOST；RS485指示灯闪烁变慢；LCD约每秒闪一次，显示`RST:24000000 WD:1 F:4`。

### 7.1 LCD诊断含义

- `RST`来自启动时保存的`RCC->CSR`。`0x24000000`包含`0x20000000`独立看门狗复位标志及`0x04000000`引脚复位标志；不能把它解释成普通上电复位。
- `WD:1`表示本次启动带有IWDG复位标志，不是当前是否正在停止喂狗，也不是累计复位次数。
- `F:4`来自心跳枚举的结束值`APP_HEARTBEAT_COUNT`，表示该次检查未发现超时；不是第4号任务故障。实际任务编号为0运动、1通信、2健康、3无线。
- 心跳编号在每次启动时重新初始化，故障详情也只保存在本次启动RAM中。因此，复位后显示`F:4`并不能排除上一次运行发生过心跳失活或栈破坏。
- 当前IWDG分频16、重装载2000，按工程标称LSI 32000 Hz计算，超时约1秒；实际时间随LSI偏差变化。每秒闪屏结合看门狗复位标志强烈提示反复复位，仍需通过启动日志或调试器确认。
- 修复后若最后一次启动仍由IWDG触发，`WD:1`可以继续保持。应检查运行时间持续增长、显示不再重新初始化及通信稳定，而不是要求该字段自动归零。

### 7.2 已确认的软件栈预算缺口

上一版在小栈`status_task`中增加完整`remote_servo_status_t`及`app_remote_servo_get_status()`调用，用于读取K5人工锁存。该调用会进一步建立双轴快照。

| 任务 | 修改前分配 | 修改前ARMCC最大调用深度 | 修复后分配 | 修复后最大调用深度 | 修复后静态余量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `status_task` | 768字节 | 1120字节 | 768字节 | 168字节 | 600字节 |
| `servo_comm_task` | 2048字节 | 2016字节 | 3072字节 | 2016字节 | 1056字节 |

状态任务的静态深度已经超过分配栈；通信任务原余量仅32字节，无法合理容纳额外上下文。栈越界可能破坏任务或共享内存，使无线回传、RS485调度和喂狗同时异常。这里确认的是静态栈预算缺陷，不冒充已抓取实物溢出现场，也不把全部症状未经复测归为唯一原因。
