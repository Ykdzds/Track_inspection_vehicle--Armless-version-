## 问题与实施范围

现场链路中存在“请求合法、源读取未拒绝、最终正常回复仍晚于屏端等待期限”的路径。屏端单次关键读超时可以触发通信待确认，随后自动STOP；正常回复不等于回复及时。原HMI服务在处理接收队列后同步构建完整字典，构建开始后到达的请求可能等待至下一次服务；完整构建耗时接近其50ms周期时，还会增加持续积压的风险。

本次取消运行路径中的周期完整字典构建，使每个状态读只复制一份已发布源、只编码所属窗口，并补齐同一事务从请求捕获到UART TC的证据。目标是消除已定位的阻塞路径；是否达到实物时限，仍需现场日志验收。主机注入45ms完整构建延迟所得约58.3ms回复完成时间属于受控复现，不能当作实物性能测量。

## 实现

- 状态窗口为 `0000/64`、`0050/32`、`0070/32`、`0090/32`、`00B0/32`、`0200/24`、`0300..045F`、`0460/96`。合法子读必须完整位于一个窗口中，单次最多125寄存器；相邻窗口之间的跨读仍拒绝。
- 普通小窗口可编码整个所属窗口；详情区只写请求交集，支持跨CAN记录、单独读取32位值的任一半字。复用已有绝对地址暂存区，不依赖其他窗口遗留内容。结果区 `0120/20` 和ARM3路由继续独立处理。
- 一次状态读只复制一次系统源。复制后及编码结束后检查这份源的年龄，不因Health发布了新源而换样重试，也不把读取时间写回源时间。每次窗口编码最多一次速度样本配对，不访问总线、不续租、不改变运动目标。
- 告警分类改为HMI任务空闲时每50ms最多观察一次，不做追赶循环。读窗口只投影已观察结果，不推进告警事件序号、发生时间或分类状态。当前停车摘要仍来自本次状态源。
- HMI任务优先级由2升为3。接收服务保留每批最多两帧、约200us检查配额；单帧同步处理耗时可超过该配额，它不等于单事务硬时限。队列仍有描述符时让出一次调度后立即继续，只有无排队描述符时等待通知或2ms期限。半帧必须等待RTU静默边界，不能忙循环提前成帧。
- UART RTU静默要求1750us、屏端300ms门禁、目标TTL 500ms、会话租约1000ms，以及STOP仲裁均保持现值。原完整编码器保留作回归对照，生产请求与维护路径均不调用它。

## 100ms源有效期与观察时效

系统源有效期仍为100ms，年龄恰为100ms允许，101ms拒绝。编码过程中被抢占导致源过期，同样返回异常；不能通过按窗口编码延长旧目标寿命。`SNAP_REJECT`冻结失败的实际原因、同一次复制的源序号/年龄及复制和编码耗时。

告警观察年龄独立计算，时间戳采用该次观察所用源的 `now_ms`，不会用维护任务执行时刻给旧观察续鲜。最近观察不超过100ms时投影其分类；超过100ms时，严重度、告警码、来源、活动与摘要标为未知，告警有效标志清零。事件序号、首次发生时间及参数保留，当前停车摘要照常更新。这是“告警观察过旧”，不代表整帧状态源过期；仅告警过旧不会替代系统源检查，也不会凭读取动作创建新告警。

`SNAP ... ordinary=last/max full_off=1`表示普通窗口编码耗时及周期全量构建已关闭。为兼容旧日志保留的 `full`、完整缓存序号/时间可能为零；不能据此判断普通状态读没有更新。`critical=last/max`为关键窗口编码耗时，`copy=last/max`为源复制耗时。

## 日志配置与时间口径

`APP/app_config.h` 中 `APP_HMI_LINK_DIAG_ENABLED` 默认1；设为0关闭新增自动文本诊断，窗口编码和调度修复继续生效。USART1为PA9 TX、PA10 RX，115200、8N1。上电前开始保存原始文本，保留BOOT、FIRST、SCREEN、SLOW、EC及周期摘要，不只截取停车后的几行。

HLD前缀的时间、boot、编号及本次新增紧凑字段均采用十六进制；`MEM free/min`、`STACK bytes`等已有具名字段按各自行格式保留十进制。不要把旧事件FIFO编号与新SLOW事务ID直接等同。

时间关系为 `cap → boundary → service → parse → submit → tc`：

| 字段 | 实际记录点 |
|---|---|
| `cap` | UART DMA接收路径捕获该请求最后一批字节的DWT时间；不是逻辑分析仪记录的最后一位 |
| `boundary` | RTU静默成立后入队的帧边界DWT时间 |
| `service` | **该帧静默边界描述符出队后、派发该帧之前**的DWT时间；不是本批服务入口时间 |
| `parse` | 协议解析器返回后的DWT时间；状态复制、窗口编码与回复构造发生在此后 |
| `submit` | UART接受本次回复提交后的DWT时间；提交成功不表示线上已发送完成 |
| `tc` | UART实际TC完成中断记录的DWT时间，包含完整回复发送 |

周期 `TIMING ... tc=last/max` 为请求捕获至UART TC的最近/历史最大周期数；`slow=warn/deadline/merged`为累计计数。DWT差值包含任务抢占，不是纯CPU执行时间。换算为毫秒：`((后时间-前时间) mod 2^32) × 1000 / hz`；168MHz时，周期数除以168000。

32位DWT在168MHz约25.57秒回绕一次。跨一次回绕应使用无符号差值；不能把两个绝对周期数直接做有符号比较，也不能用DWT绝对值独立推算长时间运行时刻。单事务若跨越完整一个计数周期，单靠这些字段无法还原；本次50ms时限分析远小于该周期。毫秒时间与boot ID用于长时间关联，新的boot应重新分组。

### SLOW两页

只有成功提交并观察到匹配UART TC的事务才进入慢事务判断。失败提交不伪造完成；源元数据只在 `flags bit0=1` 时有效。

| 行 | 字段说明 |
|---|---|
| 公共前缀 | 第三个编号为事务ID；两页用同一boot、同一事务ID关联。前缀时间为日志输出时间 |
| `SLOW p=0` | `at`为该次TC的毫秒时间；`req=start/quantity`、`fc`、`len`为请求地址/数量、功能码和回复字节数；`gen`为RX代际；其余为上述六个DWT时间点 |
| `SLOW p=1` | `src=source_ms/source_sequence`为本次复制源时间及序号；`copy/encode`为其复制/编码周期数；`total=tc-cap`；`hz`为换算频率；`warn/deadline/merged`为输出该页时的累计计数 |

`p=0`和`p=1`保存同一份不可变的首次超时事务，直至两页均被USART1整行接口接受。其间后续超时只增加计数，`merged`表示未另存详情的超时次数；计数可能在两页之间增长。读结果区、写命令及其他未复制系统源的事务可以没有源元数据，不能把零值解释为有效源。

### EC阈值、保留与输出优先级

`EC`是事件类型十六进制C，即慢事务预警，六个数据依次为：`transaction_id,start,quantity,total_cycles,cap,tc`。

- `tc-cap >= 40ms`：累计 `warn`，向固定事件FIFO记录EC。
- `tc-cap >= 50ms`：同时累计 `deadline`，若没有未输出详情则冻结SLOW两页；否则累计 `merged`。恰好50ms也计入硬门槛违例。
- 40至不足50ms的事务可以只有EC而没有SLOW详情；EC属于普通FIFO，拥塞时可能丢失。SLOW详情、首次停车及屏端首因采用独立保留，不依赖EC是否送达。

CLI格式化与整行非阻塞输出，单行小于256B、每秒预算6000B，保留现有UART缓冲。调度优先顺序为：首次停车FIRST、启动BOOT、屏端SCREEN、SLOW详情、SNAP_REJECT、100ms状态、周期摘要、普通事件FIFO、LCD组。高优先记录可能推迟后续输出，所以必须按记录时间及ID关联，不能只按相邻行推断先后。检查 `LOGGER fifo_lost/uart_drop`、`TIMING slow`和缺页；缺失EC不等于没有预警，缺失日志不能用于证明时限合格。
