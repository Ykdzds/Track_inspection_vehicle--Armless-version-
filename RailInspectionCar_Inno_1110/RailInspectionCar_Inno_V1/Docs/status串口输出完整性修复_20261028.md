# status串口输出完整性修复（2026-10-28）

## 原因和实现

现场连续六次status返回均为2047字节，固定结束于`L ramp request=1`。原调试串口环形缓存为2048字节，保留一个空槽；一次连续printf填满后，后续字节被计入dropped_bytes并丢弃。打印期间尚未调用debug_uart_service启动本次发送。

发送缓存由公共宏`DEBUG_UART_TX_BUFFER_SIZE`配置，默认8192字节，有效容量8191字节；编译期仅允许8192～32768。缓冲位于静态RAM，不增加任务栈。

每段DMA最多2047字节，保持原115200/8N1下一段约178ms的上限，保留原500ms发送恢复门限。不能直接将8191字节作为单段DMA，否则约711ms线速时间会触发原超时。环形回绕、完成中断衔接、错误恢复、满时丢弃计数和整行日志保留空间规则保持不变。

未修改运动授权、软件斜坡、H06_05/H06_06、控制源仲裁、停车及失联门限、通信协议或屏工程。保留工作区原有`APP_SERVO_CLI_DEBUG_ENABLED=0`、`APP_NRF_DIAGNOSTIC_ENABLED=0`，以及当前RTE文件内容。

## 现场验收和限制

本次未连接实物烧录、未取得现场参数回读。使用主工程Rebuild后Download，或下载上述交付HEX；冷启动，在静止状态执行一次status，等待输出结束再输入下一条命令。检查完整L/R ramp行及末尾position摘要，再执行servo left status和servo right status。通过comm stat中的usart1_tx_dma统计检查dropped在单次输出前后没有增长。

正常生产配置的预期为两轴`request=1/4541 read=1/4541 masks=3/3`，应确认readback时间属于本次启动；这些是待现场核验目标，不能用日志截断前的宏值替代。宏配置、参数回读和实测加速曲线是不同证据，本修复不声称解决57秒加速。

连续命令洪泛仍可能超过有限缓存容量，原丢弃保护继续存在。`diag=0x100`属于独立NRF初始化诊断，不由本修复清除。

回滚仅恢复本次`debug_uart.c`、`debug_uart.h`、`test_debug_uart.c`的改动，或使用交付目录保留的`before_RailInspectionCar_V1.hex`（本次构建前的本机产物，并非设备回读）。不要回退整个工程到单层加速修复之前，也不要覆盖已有两个宏和RTE工作区修改。
