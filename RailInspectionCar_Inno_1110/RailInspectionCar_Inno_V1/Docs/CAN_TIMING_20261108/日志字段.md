# CAN双侧日志

F407 `LD/HLD`头时间、boot、事件及新增紧凑词均为十六进制；旧`HLD FIRST`正文是十进制。保留原日志格式，不根据串口行顺序推测ISR先后。

## F407新增记录

`EVENT src=CS kind=10C w=`六词：原接收时间、处理时间、全局停车事件、请求序号低16位＋CAN ID高16位、请求来源、重复服务累计。它不携带command／param，需与同boot、同接收时间、同序号的原始`kind=100`（0x110）或`102/10B`（0x080）关联；缺失时未知。普通请求原始数据中byte0序号、byte1 command、byte2～3 parameter。

`FIRST src=CS/CA kind=111`：两页、每页8词，首次待发记录成功前不覆盖。字段依次如下：

| 词 | 内容 |
| --- | --- |
| 0 | 失败判定时间 |
| 1 | reason低8位、record type次8位、分段索引高16位 |
| 2 | record sequence低16位、payload长度高16位 |
| 3～7 | cookie、record开始、构建、首个TX_OK、最近TX_OK时间 |
| 8～11 | 最近TX结果处理、失败处理时间、generation、token |
| 12 | active/pending/cancelled/has_payload位0～3，重试次数高8位 |
| 13～15 | payload deadline、任务服务最大间隔、TX结果最大处理延迟 |

reason：1保留动作失败／期限到，2payload准备失败，3payload发送前期限到，4ARM首段构建预算到，5整记录／payload期限到，6TX结果到达payload截止，7重试耗尽，8ARM首段实际TX_OK超预算。reason2尚无本次TX身份，索引FFFF、cookie／开始／首末TX_OK为FFFFFFFF。没有payload时deadline可能是无意义旧字段，须看has_payload。时间差采用32位回绕算法；启动时刻0本身有效，缺有效性不能推断已经发生TX。

`HEALTH src=CS/CA p=3`总共19词，分12＋7输出；每part独立采样，不能拼成原子现场：

- part0：最大任务服务间隔、TX_OK结果处理延迟、TX_OK至下一段提交延迟、整记录完成耗时、关键记录完成耗时、四类关键记录0x11／25／13／53的最大完成间隔、失败次数、最近失败reason／时刻。
- part1：最近失败处理／TX处理时刻，当前type＋index＋pending／cancelled、sequence＋length、record开始／最近TX_OK、实际提交次数。

整记录时间起点是首次提交，终点为真实最后TX_OK；软件捕获和处理时刻不等于物理总线边沿。完成间隔以主控TX完成计，F103接收更新间隔须从上层日志核验。CS／CA同时启用时总线摘要和p3只输出一份。重复STOP服务计数新增在`HEALTH p=1`最后一词。

## F103 STOP_FIRST

详见F103工程`Docs/CANAGE_20261108.md`。三页part0／1／2冻结首个现场，source1控制陈旧、2轴陈旧、3轴不安全、4按键普通停车、5按键快速停车、6释放、7授权超时、8首零超时。标量十进制，boot／flags／valid／按键位十六进制。

`stop_req`是预期下一请求序号，并非已发送证明；不安全Fail分支为65535未知标记。后两页没有boot字段，拼接多次启动时必须保留启动banner；无banner的旧片段按单次启动文件输入。未完整三页只能报告缺页，不补猜现场。

## 分析工具

只读标准库脚本：

```powershell
python tools/analyze_link5_log.py "F407串口日志.txt" --json "F407分析.json"
python tools/analyze_link5_log.py "F103串口日志.txt" --json "F103分析.json"
```

支持原始事务、HMI完整耗时、CAN失败冻结／p3时序／10C关联、F103三页首因及缺页标记。也可使用F103独立`Tests/analyze_stop_first.py`。两端应分别输入后按boot／token／序号人工核对，不能把两个本地时间直接相减。
