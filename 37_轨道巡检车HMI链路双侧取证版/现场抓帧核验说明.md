# 17号屏被动抓帧核验

## 用途与边界

工具仅读取已有文件，不枚举或打开串口，不向屏或主控发送任何字节，不授权、不调速。当前固件仍以运行核验/Default同步交付版本.json中的BIN和哈希为准，本工具不修改固件。

用于17号最新修复版本实屏复测，核对轮询是否覆盖元数据、基础区、控制状态和四个辅助区，识别CRC正确帧、完整邮箱写、异常码及采集时间间隔。不能代替屏内接受计数、真实物理波形或机械验收。

## 输入约定

使用UTF-8 JSONL，每行记录一段原始采集字节；TX表示屏→F4，RX表示F4→屏。两个方向必须来自同一时间基准，不可将分别抓取的两个窗口拼成一次同时采集。t_ms为相对毫秒，可以是小数；hex支持空格，可分片或粘连。

```json
{"t_ms":0,"dir":"TX","hex":"01 03 02 00 00 18 44 78"}
```

这只是格式示例，不是现场证据。普通无时间十六进制文本不能自动变成真实时序；不要人工给旧抓包补时间后宣称通过200ms预算。USB串口助手以整块收到时刻标注也可能不能代表每帧线上起始时刻，精确预算优先逻辑分析仪双通道时间戳导出。

## 执行

在17号屏目录运行：

```powershell
node 现场抓帧核验.cjs "运行核验/20261018_17号最新版本双向抓包.jsonl" --out "运行核验/20261018_17号最新版本抓帧核验.json"
node --test capture-audit.test.cjs
```

输出文件若已存在则拒绝覆盖，输入始终保留。省略--out时将报告输出到终端。格式错误返回失败；命令执行成功只说明解析完成，绝不表示通信、运动或停车验收通过。

## 报告判读

- requiredRegionsMissing：应出现0000/64、0050/32、0070/32、0090/32、00B0/32、0200/24、0460/64。0120结果区按需读取，不要求只读阶段固定出现。
- readRegions：请求数及输入时间上的最大采集间隔。少于两帧不计算间隔，同时间戳多帧明确标记精度不足。
- targetTiming：共同目标请求全窗口间隔；应裁剪连续有效授权段，不能将释放后正常停止刷新算成故障，也不能在工具里删除超预算帧制造通过。
- writes：解出boot、session、序号、命令、axis和有符号rpm；mailboxViolations提示范围、有效期或邮箱格式问题，并非完整F4业务判决器。
- crcCandidateChecksFailed：扫描候选的失败次数可能重复，不能当作线上CRC坏帧精确数。丢弃及尾部字节可能是启动字节、截断、噪声或不支持帧，应查原始输入。
- physicalCommunicationVerified及motionVerified始终为false。03H回复不带地址，不将等长回复强行匹配区域，不由ACK推导授权或停车成功，也不计算跨窗口丢包率。

## 同步保存的实屏证据

先下载`运行核验/17号最新修复交付版本.json`指定的BIN和F4 HEX，未授权只读10分钟，记录两端版本/哈希、P2视频和两次间隔10秒的F4 hmi status。确认P2 B0/B5均增长、R2匹配、滑块可见，P0～P8往返三轮。RET/LEN、ADDR/FC异常与原始帧同时间保存，厂商rxLen语义尚需现场确认。

随后主动授权零速，核对结果及新状态、首零≤100ms、连续授权段目标及状态最大间隔≤200ms；通信与使能证据成立后才架空±50/±100rpm。释放、急停和失联必须关联本次停车事件、真实反馈及使能，工具解析成功不等于机械停稳。
